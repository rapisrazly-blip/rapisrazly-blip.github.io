用語辞典

まずは最初の8語(基本語)だけで十分です。残りは出てきたときに引いてください。

Claude CodeClaude Code基本語

Claude に「PCの中の作業」を任せるための道具です。チャットと違い、ファイルを読み、書き換え、コマンドを動かすところまで自分でやります。ターミナル、VS Code、デスクトップアプリ、ブラウザから使えます。

セッションsession基本語

1回の会話のまとまりです。新しく始めると、前の会話の中身は引き継がれません。引き継ぎたいものは、ファイル(CLAUDE.md など)に書いて残します。

コンテキストcontext基本語

Claude が今、頭に入れている作業机の上の広さです。会話・読んだファイル・指示がすべて載ります。机が散らかるほど、大事な指示が埋もれやすくなります。

プロンプトprompt基本語

Claude に送る指示文のことです。「お願いの文章」と読み替えて構いません。

CLAUDE.mdCLAUDE.md基本語

毎回のセッション開始時に読まれる「貼り紙」です。拡張子の .md は Markdown(見出しや箇条書きを簡単に書ける書式)の略で、中身はただのテキストです。

ターミナルterminal基本語

文字だけでPCを操作する画面です。Windows なら PowerShell、Mac なら「ターミナル」アプリがこれに当たります。

スラッシュコマンドslash command基本語

会話の入力欄に / から打つ操作ボタンです。/clear(会話を空にする)のように、Claude への相談ではなく「道具の操作」をします。

パーミッション(許可)permission基本語

Claude がファイルを書き換えたりコマンドを動かしたりする前に、あなたに「やっていいですか」と聞く仕組みです。許可の出し方で、安全さと手間のバランスが決まります。

トークンtoken

Claude が文章を数える単位です。文字数とはぴったり一致しませんが、「長いほど多く消費する」と覚えれば足ります。コンテキストの広さはトークンで決まっています。

ツールtool

Claude が使える手足です。ファイルを読む・書く・検索する・コマンドを動かす、など。許可の対象になるのは、このツールの呼び出しです。

プランモードplan mode

「まず計画だけ立てて、書き換えはしない」状態です。大きな作業の前に使うと、やり直しが減ります。

圧縮compact

長くなった会話を要約して、机の上を片付けることです。/compact で手動実行できます。

スキルskill

「この手順はこうやる」という手順書を1つのフォルダにまとめたものです。必要になったときだけ読み込まれるので、CLAUDE.md を太らせずに済みます。

サブエージェントsubagent

本体とは別の作業机で動く、お手伝いの Claude です。調べものを丸ごと任せて、結果だけ受け取れるので、本体の机が散らかりません。

フックhook

「ファイルを書いたら必ず整形する」のように、特定のタイミングで自動実行する小さなプログラムです。Claude の判断ではなく、道具のほうが必ず実行します。

MCPModel Context Protocol

外部のサービス(カレンダー・チケット管理・データベースなど)と Claude をつなぐための共通のコンセントです。差し込むと、その相手を操作できるようになります。

プラグインplugin

スキル・コマンド・フックなどを1つにまとめた配布用パックです。人が作ったものを入れて使えます。

settings.jsonsettings.json

許可・環境変数・フックなどの設定を書く設定ファイルです。CLAUDE.md が「お願い」なのに対し、こちらは「決まり」として動きます。

リポジトリrepository / repo

プロジェクトのフォルダを、変更履歴ごと管理している入れ物です。Git で管理されています。

コミットcommit

「ここまでの変更を記録した」というセーブポイントです。こまめに作るほど、戻りたいときに戻れます。

ブランチbranch

本流から枝分かれした作業用のコピーです。失敗しても本流を汚しません。

ワークツリーgit worktree

同じプロジェクトを、別のフォルダに別のブランチで同時に開く仕組みです。複数の作業を同時に進めても、互いのファイルを踏みません。

非対話モードprint mode (-p)

会話せず、1回指示して結果だけ出して終わる使い方です。claude -p "指示" の形で、スクリプトや定期実行から呼べます。

環境変数environment variable

PC全体や1つのプログラムに渡す「名前つきのメモ」です。設定値や鍵(キー)を、プログラムの外に置くために使います。

APIキーAPI key

サービスを使う権利を証明する合言葉です。チャットやコードに貼らず、.env のような別ファイルに入れます。

ハルシネーションhallucination

それらしいが事実ではないことを、AIが自信ありげに書いてしまう現象です。「根拠を出させる」「実際に確認させる」ことで減らせます。

よくある勘違い

つまずきの大半は、道具の使い方ではなく「思い込み」から来ます。

勘違い1: 前の会話のことは覚えているはず

思い込み昨日教えたルールを、今日も当然知っている。
実際セッションが変わると、会話の記憶は引き継がれません。毎回読まれるのは CLAUDE.md などのファイルだけです。「もう一度説明することになった話」を、ファイルに書いて残します。

勘違い2: CLAUDE.md に書けば必ず守られる

思い込み「絶対に〇〇しない」と書いたから、100%守る。
実際CLAUDE.md は「参考資料としての指示」で、強制ではありません。絶対に止めたい操作は、設定の拒否ルールや、フック(自動チェック)で道具側から止めます。

勘違い3: 長く書くほど丁寧で効く

思い込み思いついたルールを全部書いておけば安心。
実際長いほど机が狭くなり、守られにくくなります。公式の目安は1ファイル200行以内です。毎回必要な事実だけを残します。

勘違い4: 「できました」と言ったら、できている

思い込み完了報告をそのまま信じる。
実際「作った」と「動いた」は別物です。テストを走らせた結果、実際の画面で見た結果のように、確認した証拠を一緒に出させます。

勘違い5: 全部の許可を最初から外せば楽

思い込み確認が面倒なので、何でも自動許可にする。
実際削除・公開・課金のように取り返しがつかない操作だけは、確認を残します。読むだけの操作から、段階的に許可を増やすのが安全です。

勘違い6: 賢いモデルなら、短い指示で察してくれる

思い込み「いい感じにして」で十分。
実際「いい感じ」の基準は、あなたの頭の中にしかありません。何ができたら終わりかを、確認できる形で書きます(詳しくは「指示の出し方」)。

勘違い7: 会話が長いほど、文脈が深まって賢くなる

思い込み同じ会話を何時間も続けたほうが、事情をわかってくれる。
実際長い会話は、古い試行錯誤や脱線で机が散らかります。区切りで /clear するか、残したいことだけ要約して(/compact)続けます。

CLAUDE.md の作法

正体は「毎回読まれる貼り紙」。書く量は少なく、書く中身は具体的に。

そもそも CLAUDE.md とは

Claude Code は、セッションを始めるたびに CLAUDE.md を読みます。あなたが毎回口で説明していたことを、先に貼り紙として渡しておくイメージです。

  • 作り方: プロジェクトのフォルダで /init を実行すると、中身を調べて雛形を作ってくれます
  • 確認: /context を実行すると、今読み込まれている「Memory files」の一覧が見えます
  • 書式: ただのテキスト(Markdown)なので、メモ帳でも開けます
POINTClaude は CLAUDE.md を「指示の資料」として読みます。強制的に動かす設定ファイルとは別物です。

出典: 公式ドキュメント「How Claude remembers your project」(2026-10 確認)

置き場所は4種類。ふだん作るのは1つだけ

種類場所使いどころ
ユーザー~/.claude/CLAUDE.md全プロジェクト共通の、自分の好み(口調・言語など)
プロジェクト./CLAUDE.md または ./.claude/CLAUDE.mdそのプロジェクトの決まり。チームと共有できる
ローカル./CLAUDE.local.md自分専用のメモ。.gitignore に入れて共有しない
組織OSごとの管理用の場所会社全体の方針(個人利用ではまず使わない)

はじめは、プロジェクトのフォルダに1枚だけで十分です。個人の好みが増えたら、ユーザー用に移します。

読み込まれ方のルール

  • 作業中のフォルダと、その上の階層にある CLAUDE.md は、起動時にまとめて読まれます(上書きではなく、合体)
  • 下の階層(サブフォルダ)の CLAUDE.md は、そのフォルダのファイルを Claude が読んだときに読まれます
  • 別のファイルを取り込みたいときは @ファイル名 と書きます。ただし取り込んだファイルも起動時に読まれるので、長さは減りません

書くべきものは「もう一度説明することになった話」

  • 同じ間違いを2回されたとき
  • 前回と同じ訂正を、また打ち込んだとき
  • 新しく入った人にも説明が必要な話(ビルドの手順、フォルダの役割、命名の決まり)
GOOD思い出したルールを全部書くのではなく、「2回説明した」が貯まった時点で1行足す。これだけで貼り紙は育ちます。

効く書き方は4原則

  1. サイズ: 1ファイル200行以内を目標にします
  2. 構造: 見出しと箇条書きでグループ分けします。ぎっしりの文章は読まれにくくなります
  3. 具体性: 確認できるところまで言葉を下ろします
  4. 一貫性: 矛盾する2行を残しません。どちらを取るかは運任せになります
BAD「コードをきれいに整える」「テストをちゃんとする」
GOOD「インデントは半角スペース2つ」「コミット前に npm test を実行する」

サブフォルダごとに置くべきか

基本は置きません。理由は3つです。

  1. どこに何が書いてあるか把握しづらくなり、矛盾に気づけなくなる
  2. 読まれるタイミングがフォルダ次第になり、効くかどうかが読みにくい
  3. 「特定のファイルにだけ効かせたい」なら、もっと向いた仕組み(ルールファイルやスキル)がある
POINT置いてよいのは、そのフォルダだけに通じる決まりが確かにあるときだけ。迷ったら、まず1枚に戻します。

そのまま使えるひな形

# プロジェクト名

## このプロジェクトは何か
(1〜2行で。誰が何のために使うか)

## よく使うコマンド
- テスト: npm test
- 起動:   npm run dev

## フォルダの役割
- src/     本体のコード
- docs/    説明書
- data/    入力データ(手で編集しない)

## 守ること
- 変更後は必ずテストを実行してから報告する
- 削除・公開・課金を伴う操作は、先に私に確認する
- APIキーはチャットに貼らず、.env に書く

## 返答のしかた
- 結論を1行目に書く
- 確認していないことは「未確認」と書く

最後の「返答のしかた」のように、AIとの付き合い方も書けます。書く内容は人によって違って構いません。

よくある失敗5つ

1思いついたことを全部書く
2「丁寧に」「適切に」で終わらせる(何をもって丁寧かが無い)
3古い記述を消さずに、下に追記だけする
4コードを読めばわかることまで書く
5長い手順書を丸ごと入れる(手順はスキルに分ける)

知っていると得する小技

  • /memory で、今読まれているメモリファイルの確認と編集ができます
  • 会話を圧縮(/compact)しても、CLAUDE.md は読み直されて残ります
  • CLAUDE.md が長くなったら、/doctor prompt-audit で古い記述や矛盾の点検ができます(新しめのバージョンが必要。出ない場合は claude --version を確認)
  • CLAUDE.md(あなたが書く)と「自動メモリ」(Claude が自分でメモする)は別物です

フォルダ構成

フォルダの形が整っていると、Claude も人も迷いません。

大原則は4つ

  1. 名前で中身がわかるようにする(utils/ や misc/ は作らない)
  2. 変わる値は、プログラムの外に出す(設定ファイルへ)
  3. 人が書く場所と、機械が書く場所を分ける(手書きと自動生成を混ぜない)
  4. 同じことを2か所に書かない(正本を1つ決める)

.claude/ の中身

場所入れるもの
.claude/settings.jsonチームで共有する設定(許可・フックなど)
.claude/settings.local.json自分だけの設定(共有しない)
.claude/skills/名前/SKILL.mdスキル(手順書)
.claude/agents/名前.mdサブエージェントの定義
.claude/rules/テーマ別のルール分割
POINTサブエージェントの置き場は .claude/agents/ です。似た名前の別フォルダに置いても読まれません。

  src/               コード
  README.md          人向けの説明

指示の出し方

まず押さえる6つ。これだけで、やり直しが目に見えて減ります。

1. ゴールでなく「終わったと言える条件」を書く

BAD「ログイン画面を作って」
GOOD「ログイン画面を作って。メールとパスワードを入力でき、間違えたら赤字で理由が出て、成功したらトップへ移る。テストを1本書いて、通ることを見せて」

条件が書いてあれば、Claude は自分で確かめながら進められます。

2. 最初に読ませるものを名指しする

GOOD「まず @docs/spec.md と @src/login.js を読んでから始めて」

探させるより、置き場を教えるほうが速く確実です。@ を打つと、ファイルを候補から選べます。

3. 大きい仕事は「計画 → 承認 → 実行」に割る

STEP 1計画だけ出させる(書き換えない)
STEP 2あなたが読んで、直す
STEP 3OK を出してから実行させる

プランモード(Shift+Tab で切り替え)を使うと、書き換えのない状態で計画を作れます。

4. 「やるな」は気持ちでなく動作で書く

BAD「なるべく勝手に変えないで」
GOOD「src/ 以外のファイルは編集しない。削除する前に一覧を見せて、私の返事を待つ」

5. 確認のしかたも頼む

GOOD「終わったら、テストの出力・変更したファイルの一覧・確認していないこと、の3つを分けて報告して」

「確認済み」と「推測」を混ぜて報告させないための一言です。

6. 一度にたくさん頼まない

1回の依頼は、1つの目的に絞ります。「A をして、ついでに B と C も」は、どれかが雑になりやすくなります。終わってから次を頼みます。

依頼のひな形

【目的】何のためにやるか(1行)
【対象】触ってよい場所 / 触らない場所
【やること】箇条書きで
【終わりの条件】何が確認できたら完了か
【報告】確認したこと / していないこと を分けて

作業の型

作業の種類ごとの、基本の流れです。

基本の4拍子

1 探る関係するファイルを読ませる
2 計画するやることを短く出させる
3 作る小さく区切って実装させる
4 確かめるテスト・実行で証拠を出させる

順番を飛ばすと、やり直しが増えます。特に「探る」を飛ばすと、的外れな変更が起きやすくなります。

バグを直すとき

  1. エラーメッセージは、要約せず原文のまま貼る
  2. 「いつから・何をしたら・何が起きるか」を1行で添える
  3. まず原因を説明させ、直すのはその後にする
  4. 直したら、同じ操作で再現しないことを確認させる

新しい機能を足すとき

  1. プランモードで計画だけ出させる
  2. 計画を読み、気になる所を直す
  3. 小さな単位で作らせ、単位ごとにコミットする
  4. 最後に「元からあった機能が壊れていないか」も確認させる

文章・資料をつくるとき

  1. 読者と目的を先に書く(誰が読んで、どうなってほしいか)
  2. 素材と、出してよい根拠を渡す
  3. 下書きを出させ、直したい所だけ指摘する
  4. 数字・固有名詞・出典は、最後に自分の目で確認する
POINT文章でも「確認していない数字は、断定しない」を最初に頼むと、事故が減ります。

  • 調べものは、サブエージェントに任せて結果だけ受け取る

こまめにセーブする(コミット)

動いた時点でコミットしておけば、次の変更が失敗しても戻れます。大きな変更の前には、必ずその時点の状態を記録します。

戻したいときは、/rewind で会話とファイルの状態を前の時点へ巻き戻せます(使えない環境は /help で確認)。

許可は「読むだけ」から広げる

はじめファイルを読む・検索するだけを許可
慣れたらテスト・ビルドなど、よく使う安全なコマンドを許可
最後まで削除・公開・課金は、毎回確認を残す

許可は /permissions や settings.json で管理します。

鍵と個人情報は絶対にチャットに貼らない

NGAPIキーをチャットに貼って「これ使って」と頼む。
OK空欄の .env を用意し、自分で値を書き込む。Claude には「.env を参照する」とだけ頼む。

公開するリポジトリに .env を含めていないか、公開(push)の前に必ず確認します。

並行作業はワークツリーで

2つの作業を同時に進めるときは、同じフォルダで2つ走らせず、別のワークツリー(別フォルダ)に分けます。互いのファイルを上書きし合う事故を防げます。

記録は「事実」と「推測」を分けて残す

作業メモには、確認した事実・聞いた話・推測・未確認を混ぜず、ラベルを付けます。後で読む自分が、どこまで信じてよいか判断できます。

定期的な棚卸し

月に一度、CLAUDE.md を読み返して、古い記述・矛盾・もう不要な決まりを消します。足すより、削るほうが効きます。

詰まったとき

症状から引ける早見表です。

症状別

症状まず疑うことやること
同じ間違いを何度もする貼り紙に書いていない / 矛盾しているCLAUDE.md に具体的な1行を足す。矛盾する行は消す
書いたルールを守らない長すぎて埋もれている / あいまい短くし、確認できる言い方に直す。絶対なら設定やフックで止める
会話が噛み合わなくなってきた机が散らかっている/compact、それでも駄目なら /clear して要点だけ貼り直す
勝手に大きく変更される範囲を指定していない触ってよい場所を明記。プランモードで先に計画を見る
「できた」のに動かない確認の証拠を取っていないテスト・実行結果を出させる。出せないなら、その理由を報告させる
確認の許可が多すぎる安全な操作が未許可読むだけ・テストなど、安全なものから許可に追加
claude が見つからないインストール先がPATHに無い新しいターミナルを開き直す。claude --version で確認。公式のインストール診断を見る
日本語が文字化けする(Windows)文字コードの違いファイルは UTF-8 で保存。出力側の文字コードも合わせる
変なファイルを作られた置き場の指定がないCLAUDE.md にフォルダの役割を書く

それでも駄目なとき

  1. エラーは要約せず、原文のまま貼る
  2. 「やったこと」「期待した結果」「実際の結果」を1行ずつ書く
  3. 新しいセッションで、その3行だけを渡して聞き直す
  4. 同じ失敗を2回したら、手段を変える(別のやり方・別の担当に頼む)
POINT粘って同じことを繰り返すより、「詰まっている」と言って切り替えるほうが早く終わります。

便利な機能

知っておくと一段ラクになる機能です。

プランモード

Shift+Tab でモードを切り替え、「計画だけ作って書き換えない」状態にできます。大きな作業の最初に使います。

@ でファイルを指定

入力欄で @ を打つと、ファイル名の候補が出ます。選ぶと、そのファイルを読ませる指示になります。

履歴を再開する

前の会話の続きから始めたいときは、claude --continue(直近を続ける)や claude --resume(一覧から選ぶ)を使います。会話中なら /resume です。

巻き戻し

Esc を2回押すか /rewind で、会話とファイルの状態を前の時点に戻せます(環境により表示が違う場合があります)。

スキル

繰り返す手順を .claude/skills/名前/SKILL.md に書いておくと、/名前 で呼び出せます。説明文(description)に「どんなときに使うか」を書いておくと、Claude が自分で選ぶ手がかりになります。

サブエージェント

調べもの・レビューなどを別の担当に任せられます。.claude/agents/ に定義を置くか、/agents で管理します。道具を制限した担当(読むだけのレビュー係など)を作ると、事故が減ります。

フック

「書き換えの前後」「プロンプト送信時」「セッション開始時」など、決まったタイミングで自動実行できます。整形・安全チェック・記録に向いています。

非対話モード

claude -p "この差分を見て、危ない点を3つ挙げて"

会話せずに結果だけ返します。スクリプトや定期実行に組み込めます。

繰り返し・予約

/loop は会話の中で同じ指示を繰り返します。定期的なクラウド実行(/schedule)や、デスクトップアプリの予約タスクもあります。

連携・拡張

外のサービスとつなぐ、機能を足す。

MCP で外部サービスにつなぐ

カレンダー・チケット管理・チャットなど、対応するサービスとつなげると、Claude から読み書きできます。追加は claude mcp add や /mcp で管理します。

注意つなぐ = 相手のデータに触れる、ということです。送信・削除・公開ができる接続は、使う前に何が起きるかを確認します。

プラグインで一括導入

スキル・コマンド・フックなどが1つにまとまった配布パックです。入れる前に、中身(何を実行するか)を読みます。出所の分からないものは入れません。

IDE・デスクトップ・ブラウザ

同じ Claude Code が、VS Code・JetBrains・デスクトップアプリ・ブラウザでも動きます。CLAUDE.md や設定は共通で使えます。

GitHub などと連携して自動化

GitHub Actions と組み合わせると、PR のレビューや Issue の仕分けを自動化できます。最初は、読むだけ・コメントするだけの範囲から始めます。

Agent SDK で自作する

Claude Code と同じ道具立てを使って、自分専用の自動化プログラムを作れます。プログラミングが前提なので、慣れてから挑戦します。

拡張を増やす順番

1CLAUDE.md を育てる
2繰り返す手順をスキルにする
3必ずやることをフックにする
4外部サービスを MCP でつなぐ

重いものから入れると、管理しきれなくなります。軽いものから積みます。
